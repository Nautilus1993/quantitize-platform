# Quantitize Platform：21 类 Pose 模型适配分析与实施计划

> 文档日期：2026-09-03
> 分析对象：`<local-data-root>\model.pt`（旧 2 类）与 `<local-data-root>\weights\best.pt`（新 21 类）
> 项目代码：`<repository-root>`，对应 H200 `/data3/ywang/quantitize-platform`
> 本次范围：只读结构分析与静态代码审计；没有修改平台代码、模型、配置或 FPGA 文件，也没有执行推理、量化、ONNX 导出或回归测试。

## 1. 结论先行

两个 `.pt` 都是 Ultralytics 8.3.98 保存的 YOLOv8x-Pose-P6 模型。主干、颈部、四尺度检测头、边框回归分支和关键点分支都相同；新模型不是另一套网络结构，核心变化是分类数从 2 增至 21，导致四个尺度的分类末端卷积由 2 个真实输出通道增至 21 个。

因此，平台适配的重点不是重写整个量化器，而是把 `nc`、类别名和输出布局变成贯穿“模型—数据集—任务配置—ONNX/NMS—FPGA 后处理”的明确接口，并消除当前的 2 类、6 类和 1280 尺寸硬编码。

FPGA 侧有一个有利条件：当前权重形状表已经把四个分类末端层 `L35_s02`～`L38_s02`预留为 32 个物理通道。21 个有效类别仍能放进 32 通道容器，所以在现有通道对齐规则成立时，`ALL_WT.bin` 的总体布局和后续层偏移可能保持不变。但这只是静态代码推断，必须用新模型导出的 ONNX、逐层 `.bin`、`metadata.json` 和 FPGA 实测确认。尤其不能把“物理 32 通道”误当成“有效 32 类”。

### 2.2 网络结构差异

| 项目 | 旧 2 类 | 新 21 类 | 判断 |
|---|---:|---:|---|
| 模块数 | 31 | 31 | 相同 |
| 最后一层 | index 30，`Pose` | 相同 | 相同 |
| 输入特征层 | `[20, 23, 26, 29]` | 相同 | 四尺度 P6 头不变 |
| 检测尺度数 `nl` | 4 | 4 | 相同 |
| `reg_max` | 16 | 16 | 相同 |
| 类别数 `nc` | 2 | 21 | **变化** |
| 关键点定义 `kpt_shape` | `[2, 3]` | `[2, 3]` | 2 个关键点，每点 x/y/visibility，不变 |
| 检测头内部 `no=64+nc` | 66 | 85 | **变化** |
| 总参数量 | 99,169,344 | 99,193,740 | +24,396 |
| checkpoint 大小差 | — | +47,872 B | 仅小幅增长 |

唯一发生形状变化的模型参数是四个尺度的分类末端卷积：

```text
model.30.cv3.{0,1,2,3}.2.weight: [2, 320, 1, 1] -> [21, 320, 1, 1]
model.30.cv3.{0,1,2,3}.2.bias:   [2]            -> [21]
```

参数增量可以完全解释：

```text
19 个新增类别 × (320 个权重 + 1 个 bias) × 4 个尺度 = 24,396
```

以下分支没有变化：

- 边框 DFL 末端 `cv2.*.2`：64 个通道；
- Pose 末端 `cv4.*.2`：6 个通道，即 `2 × 3`；
- backbone/neck 的卷积拓扑和参数形状；
- 四个尺度及 stride 结构。

## 3. 输出张量应如何理解

这里需要区分三种宽度，避免 FPGA 和软件团队说的是不同对象：

1. 检测头属性 `no=64+nc`：旧模型为 66，新模型为 85。64 是四边 DFL 分布，不包含 Pose 的 6 通道。
2. 解码前每个候选点的总逻辑数据：`64 + nc + 6`，旧模型 72，新模型 91。
3. Ultralytics 常见导出后的最终解码输出：`4 + nc + 6`，旧模型预计 12，新模型预计 31。

“预计”是因为本次按要求没有导出 ONNX。实施阶段必须读取实际 ONNX 的输入、输出和中间节点形状，不能只凭公式改 FPGA。

若固定输入为 1280、stride 为 8/16/32/64，四尺度候选点数预计为：

```text
160×160 + 80×80 + 40×40 + 20×20 = 34,000
```

这与现有 `layer_wt_shapes.py` 中 `L43: (32, 34000, 1, 2)` 的 34,000 一致。最终有效输出 31 通道也恰好能放进 32 通道物理槽位；但 `L43` 的第二个维度和最后的 `1,2` 各自代表什么、FPGA 如何读取，仍需与 `L43_bin_process` 和 RTL/上位机协议共同确认。当前检查的工作树中没有找到被 `01_rename_wt_files.py` 导入的 `L43_bin_process.py`，需要先确认它是在镜像内、未提交文件还是外部依赖。

## 4. 平台代码需要适配的内容

### 4.1 P0：建立唯一的模型/数据集契约

当前存在三套默认值：

- `pipeline/runner/_lib/job_config.py:38,71` 默认 `nc=6`；
- `pipeline/runner/_lib/validate_input.py:18,93` 默认六类名称和 `nc=6`；
- `pipeline/engine/simple_onnx_inference.py:148,281,382` 默认 `nc=2`。

共享数据集路径之所以能运行旧 2 类模型，是因为 `shared_datasets.py:626-632` 会用测试集注册表覆盖任务的 `cfg.nc`。这不是模型与数据一致性的证明：如果选错测试集，新 21 类模型仍可能以 2 或 6 类进入 NMS，造成输出切片错误、漏检或把关键点通道当类别通道。

建议定义并持久化一个版本化 `model_contract`，至少包含：

```json
{
  "schema_version": 1,
  "task": "pose",
  "nc": 21,
  "class_names": {"0": "agaier", "...": "...", "20": "moon"},
  "kpt_shape": [2, 3],
  "input_size": 1280,
  "strides": [8, 16, 32, 64],
  "checkpoint_sha256": "94125B...E2F"
}
```

任务创建时应进行三方校验：模型元数据、测试集注册信息、任务配置必须一致；类别键必须连续覆盖 `0..20`。不一致时应在任务启动前失败，并明确显示哪两方冲突。不要仅增加一个可手填的 `nc` 输入框，因为手填值仍可能与模型不一致。

### 4.2 P0：网页与 API 建单链路

- `apps/web/templates/new_task.html` 当前只让用户选模型和共享数据集，不显示模型类别信息。
- `apps/web/app.py:387-409` 固定发送 `imgsz=1280`，不发送 `nc`；API 虽在 `apps/api/app.py:237-264` 接受可选 `nc`，网页没有使用。
- `apps/api/create_task.py:242-259` 先创建配置，再由所选测试集覆盖 `nc`，随后才校验标签。
- ZIP 建单路径只有在上传包自带 `job_config.json` 时才能覆盖默认 `nc=6`，且没有与 `.pt` 交叉校验。

建议流程：上传模型后在隔离检查器中提取 `task/nc/names/kpt_shape`，网页显示摘要；选择数据集后 API 对比契约，匹配才允许创建或启动。共享数据集注册表需新增 21 类测试集元数据和完整类别表；标定集也应记录适用模型族、预处理和覆盖说明。

### 4.3 P0：输入尺寸必须只有一个事实来源

`JobConfig.imgsz` 和网页当前是 1280，但 `pipeline/engine/quantitize.py:814-820` 在实际 PT→ONNX 导出时再次硬编码 `imgsz=1280、device='0'`，runner 没有把 `cfg.imgsz` 传给它。21 类任务短期若坚持 1280 不会触发差异，但这是 FPGA 候选点数和 `L43=34000` 的结构约束，不能伪装成可配置项。

实施时二选一：

- 明确平台/FPGA ABI 只支持 1280，在 API 中拒绝其他值；或
- 把 `imgsz` 真正贯穿导出、评估、FPGA 打包、L43 生成和硬件描述，并为不同候选点数生成不同 ABI。

在当前硬件形状表下，第一种风险更低。

### 4.4 P1：评估、展示和类别覆盖

- `01_pt_eval.py`、`02_onnx_eval.py` 已把 `cfg.nc` 传给评估/NMS，主路径可扩展到 21 类，前提是 `cfg.nc` 正确。
- `eval_common.py` 的默认 `nc=6` 应消除或改为必传，避免其他调用者回退到错误值。
- `apps/api/artifacts.py:124` 从测试集注册表取类别名，缺失时退回 `class_<id>`；新测试集必须提供完整 21 类名称。
- `eval_fpga_results.py` 当前按 IoU 匹配，但没有在匹配中约束 `class_id`，也没有输出 21 类逐类指标；这会掩盖“框位置正确、类别完全错误”的 FPGA 问题。
- `03_yolo_labels_to_json.py` 目前输出框的 `class_id`，但 `keypoints` 固定为空；若本需求需要验证两个关键点，必须补齐 GT 转换和 FPGA 结果格式。

应增加：每类样本/实例覆盖统计、每类 P/R/F1、类别混淆、宏平均与微平均，以及 PT→FP16→INT8→FPGA 的同图逐级差异。21 类里稀有类别不能被总体平均值掩盖。

### 4.5 P1：量化和节点抽取的稳健性

量化主体按 ONNX 图和卷积形状工作，未发现直接写死 2 类的主路径；类别层变宽通常能被处理。但以下位置依赖导出图名称或固定结构：

- `check_certain_layer_multi.py:826-866` 写死 `/model.30/Concat_5`、`Reshape_9`、四组 `cv2/cv3/cv4` 节点；
- `get_conv_name.py:140-159` 固定 Pose 四尺度分支；
- `quantitize.py:310-418` 按节点类型和名称关键字生成排除列表。

两个 checkpoint 使用同版本 Ultralytics 且拓扑相同，所以节点名大概率稳定；仍必须以实际 ONNX 图做结构断言。更稳妥的做法是按输出关系、op type 和 initializer 形状定位节点，并把预期节点集合与实际集合的差异作为失败条件，而不是某个节点找不到后继续生成不完整 `.bin`。

## 5. FPGA 端需要重点确认的问题

### 5.1 四个分类末端层的有效通道与填充通道

现有映射很可能是：

```text
cv2 四尺度 -> L31..L34，真实/物理输出 64
cv3 四尺度 -> L35..L38，真实类别 2，物理输出 32
cv4 四尺度 -> L39..L42，真实关键点 6，物理输出 32
```

新模型的 `cv3` 原始 INT8 权重每尺度从 `2×320=640 B` 增至 `21×320=6,720 B`。形状表目标仍是 `32×320=10,240 B`，所以正确做法应是保留前 21 个真实输出通道并把通道 21～31 填零。

当前 `01_rename_wt_files.py:112-138` 的通用函数在输入比目标小时尾部补零，在输入大于目标时直接截断。对本次 21→32 的输出通道补齐，从扁平顺序看可能正确；但它没有验证被补区域、维度语义和量化参数是否同步。因此需要增加明确的“逻辑 shape→物理 shape”校验和日志。更重要的是，未来若 `nc>32`，当前代码会静默截断模型权重，这是必须改成硬失败的安全问题。

### 5.2 `.bin` 大小与偏移

`02_merge_wt_files.py` 以静态 `WT_SHAPES` 验证文件并顺序拼接，生成 `metadata.json` 和 `weight_offset_table.h`。如果四个分类层最终都对齐为 32 通道，那么新旧 `ALL_WT.bin` 总大小和各层偏移理论上可保持一致；内容和哈希一定不同。

实施时必须验证而不是假定：

- 四个原始分类层的逻辑 shape 是 `[21,320,1,1]`；
- 四个 FPGA 权重层的物理 shape 是 `[32,320,1,1]`；
- 填充通道 21～31 全零；真实通道 0～20 没有被移动或截断；
- 每层量化 scale/zero-point/bias 与 21 个真实通道一一对应，填充通道采用硬件认可的中性值；
- 合并后的 offset/size 与生成的 C 头文件完全一致；
- FPGA 加载的表来自同一构建产物，不能继续使用旧头文件配新 `.bin`。

### 5.3 输出缓存、DMA 和后处理

即使权重区不扩大，运行时输出语义也变了：

- 分类 argmax/sigmoid 只能遍历 21 个有效通道，不能遍历补零后的 32 个通道；
- 解码后类别区间从 `[4,6)` 变为 `[4,25)`，关键点起始位置相应后移到 25；
- 若 FPGA 暴露的是解码前数据，则分类分支从 2 变 21，原始总逻辑宽度从 72 变 91；
- 若暴露的是最终解码数据，则逻辑宽度预计从 12 变 31；
- 缓存 stride、burst 长度、DMA 长度、CPU/FPGA 共享结构体、JSON 序列化和显示字符串都要按实际接口检查；
- 21 类阈值是否统一使用一个 `conf`，还是需要逐类阈值，应由验证数据决定，不能直接沿用旧 2 类阈值结论。

### 5.4 二进制 ABI 应可自描述和防错配

当前 `metadata.json` 主要记录权重文件名、物理 shape、offset 和 size；FPGA 测试包的 `job_meta.json` 有 `nc`，但没有类别表、模型哈希、关键点定义和权重包哈希。建议给交付包增加版本化 manifest：

- checkpoint、ONNX、`ALL_WT.bin`、`ALL_BN.bin` 的 SHA-256；
- task、`nc`、有序类别表、`kpt_shape`；
- 输入大小、stride、候选点数；
- 每层逻辑 shape、物理 shape、padding 规则、dtype、量化 scale/zero-point；
- offset、size、字节序、ABI 版本和最低兼容 FPGA/host 版本。

加载时应核对 ABI 版本和哈希，不匹配则拒绝运行。仅靠文件名和固定加载顺序无法防止旧固件、新权重和旧类别表混装。

## 6. 数据与量化质量

21 类模型不能直接复用只覆盖 `aituosha/moon` 的旧测试集来验收。

- 标定集不依赖标签参与计算，但图片分布应覆盖 21 类的典型尺度、亮度、背景、姿态和传感器预处理，否则激活范围可能偏向少数类别。
- 测试集必须使用与模型完全一致的 0～20 类别 ID，并覆盖每一类；应单独列出零覆盖和低覆盖类别。
- `preprocess_mode` 是模型接口的一部分。应先确认新模型训练时的 RGB/灰度约定，不能因为旧任务使用 `grayscale_r_channel` 就直接照搬。
- checkpoint 训练参数显示训练 `imgsz=1024`，平台/FPGA 当前按 1280 导出和评估。这不必然错误，但要把 1280 下的精度和性能作为新的实测基线。

## 7. 分阶段实施计划

### 阶段 0：冻结接口与素材

1. 固定两个 checkpoint 的哈希、Ultralytics/ONNX Runtime 版本和导出参数。
2. 由模型负责人确认 21 类顺序、每类业务含义、关键点定义和训练预处理。
3. 准备 21 类共享标定集/测试集清单，输出每类覆盖统计。
4. FPGA 团队确认输入 1280、四尺度、32 通道对齐、L43 和输出缓冲的真实 ABI。

完成条件：形成经双方确认的 `model_contract.json` 草案，所有类别和 tensor 语义无歧义。

### 阶段 1：只做模型与 ONNX 合同探针

1. 在隔离环境加载 checkpoint 并生成结构清单。
2. 导出 FP16 ONNX，记录输入输出 shape、34,000 候选点、实际节点名称。
3. 对比新旧 ONNX，证明除四个分类末端和相关 concat/reshape 常量外，其余卷积形状不变。
4. 检查最终输出到底是 31 通道还是其他布局，并据此冻结 FPGA 接口。

完成条件：自动化断言通过；不存在“按经验猜输出”的项目。

### 阶段 2：平台配置与建单适配

1. 增加安全的 checkpoint 元数据检查器与契约文件。
2. 去掉主路径中的 `nc=2/6` 回退，改为模型元数据驱动并与数据集交叉校验。
3. 注册 21 类共享数据集及类别名；网页显示模型/数据集匹配状态。
4. 将输入尺寸固定为受支持的 1280，或完整贯通 `imgsz`；当前建议固定并显式拒绝其他值。
5. 更新指标页和任务 manifest，保存完整类别表与哈希。

完成条件：选错 2 类数据集时建单/启动必定失败；正确 21 类数据集时配置中只有一个 `nc=21` 来源。

### 阶段 3：量化与 `.bin` 生成适配

1. 对分类层建立逻辑 21→物理 32 的显式 padding 规则。
2. 把任何逻辑输出超过 32 的情况改成硬失败，禁止静默截断。
3. 核对分类层的权重、bias、scale、zero-point 和层名映射。
4. 生成带完整 ABI 和哈希的 manifest；核对 `metadata.json` 与 `weight_offset_table.h`。
5. 证明旧 2 类任务仍可按 2→32 规则构建，避免破坏兼容性。

完成条件：逐层反解 `.bin` 后，21 个真实通道与 ONNX 量化 initializer 一致，11 个 padding 通道满足硬件约定。

### 阶段 4：FPGA 后处理适配

1. 更新有效类别数、类别表、分类循环和 tensor 切片。
2. 核对缓存/DMA/stride，不把物理 32 通道暴露为 32 类。
3. 更新结果 JSON，使每个框带合法 `class_id`、置信度和两个关键点。
4. 加入固件/上位机 ABI 版本和模型包哈希检查。

完成条件：固定输入在 FPGA 与 ONNX 上的类别 ID、框、置信度和关键点语义一致。

### 阶段 5：分层验收与回归

1. PT 基线：21 类逐类指标和关键点误差。
2. FP16 ONNX：与 PT 做同图输出差异。
3. INT8 ONNX：量化精度损失、逐类退化和稀有类退化。
4. 逐层 `.bin`：重点比较 L35～L43 输入输出。
5. FPGA：与 INT8 ONNX 对齐，分析定点舍入、padding 和 DMA 差异。
6. 旧 2 类 golden task 回归，确保平台兼容性。

完成条件：阈值由业务方预先给定；不能用“总体均值看起来接近”替代逐类、关键点和坏例检查。

## 9. 当前不能直接下结论的项目

以下内容必须等后续获准导出/测试后确认：

- 新 ONNX 的实际最终输出 shape、节点名称和 concat 顺序；
- INT8 分类层量化参数是 per-tensor 还是 per-channel，以及 bias 的实际打包格式；
- `L43_bin_process.py` 的真实来源和 `L43 (32,34000,1,2)` 的完整语义；
- 新旧 `ALL_WT.bin` 是否确实同大小/同 offset；
- FPGA 输出是解码前 91 维、解码后 31 维，还是自定义 32 通道布局；
- 21 类数据和训练时预处理是否与平台当前灰度流程一致；
- 可接受的 PT→INT8→FPGA 精度损失阈值。

在这些问题确认前，不建议直接从网页启动新模型的完整量化任务，更不建议把生成的 `.bin` 交给现有 FPGA 固件加载。
